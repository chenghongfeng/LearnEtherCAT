## 0. 先建立正确的能力边界

### 0.1 一句话系统模型

> 主站负责**请求、编帧、调度和观察**；ESC 负责**网络转发、地址匹配、
> 内存映射和 SM/FMMU 机制**；从站协议栈与设备应用负责**接受状态迁移、
> 处理邮箱、维护对象字典和执行设备行为**。

不能用一条“主站写 PDO 成功”推断物理输出已经发生。下面四个判断必须分开：

| 判断 | 第一手证据 | 它不能证明什么 |
|---|---|---|
| 帧是否到达并返回 | 收到帧、链路状态、WKC | 数据语义是否正确 |
| 从站是否接受状态 | `AL_STATUS` + `AL_STATUS_CODE` | 从站应用是否完成了设备动作 |
| 过程数据是否配置正确 | FMMU、SM、PDO 映射、iomap、WKC | 数据是否新鲜、输出是否已施加 |
| 物理动作是否发生 | MCU PDI 读到的值、应用日志、GPIO/PWM、传感器 | 下一周期仍会保持 |

主站工程师的核心能力不是背 API，而是能从这些彼此独立的证据中找出
最早出现异常的一层。

### 0.2 学完本文应达到的水平

1. 能画出并解释从 `iomap` 一个字节到从站执行器的完整数据链。
2. 能区分逻辑地址、ESC 内部地址、MCU 物理地址和对象字典地址。
3. 能解释 FMMU、SyncManager、PDO、OD、ESI 和 SII 各自解决什么问题。
4. 能看懂 ESM 迁移条件、AL 错误码和看门狗超时，而不是只看见“超时”。
5. 能为周期任务、邮箱任务和中断定义职责、优先级与有界执行时间。
6. 能解释 `volatile`、原子操作、内存屏障和 cache 维护分别解决什么问题。
7. 能在 Linux 上测量周期抖动，区分平均延迟和尾延迟。
8. 能安全完成单从站 Bring-up，并在仿真正常、实机失败时提出可验证假设。

### 0.3 明确不要求现在掌握的内容

- 不需要会设计 EtherCAT 网络接口或 PHY 的 PCB 布局。
- 不需要会从零实现 ESC 的转发状态机或 FMMU 硬件。
- 不需要达到从站固件架构师、EMC 工程师或功能安全认证工程师的水平。
- 不需要先学完整个 NuttX 内核或 ARM Cortex-M 体系结构课程。
- 不需要用“自己写一个从站协议栈”来证明理解；应先能读懂并测试现有实现。

这些是后续协作能力，不是主站开发第一阶段的前置条件。

## 1. 全系统因果链

### 1.1 输出方向

```text
设备应用设定值
    │
    ▼
主站 iomap 中的输出字节
    │ Bus::buildFrames / 逻辑寻址
    ▼
LRW 等 PDU
    │ Frame / Link / Socket
    ▼
Linux 网卡或 Windows Npcap
    │ Ethernet PHY、电缆
    ▼
ESC 端口 0/1/2/3
    │ ESC 就地处理，然后继续转发
    ▼
FMMU 把逻辑地址映射到 ESC 物理地址
    │ SM 提供方向、边界和同步语义
    ▼
ESC DPRAM 中的输出过程数据
    │ PDI：SPI、内存映射或并行接口
    ▼
MCU/SoC 获取输出缓冲区
    │ 从站 PDO 层 / 对象字典别名
    ▼
设备应用（GPIO、DAC、PWM、通信命令）
    │
    ▼
真实执行器
```

### 1.2 输入方向

```text
传感器 / 设备状态
    │
    ▼
设备应用输入缓冲区
    │ PDO::updateInput
    ▼
ESC DPRAM 的输入过程数据
    │ FMMU 把 ESC 物理地址映射进逻辑地址
    ▼
主站周期帧读回
    │ WKC 检查
    ▼
主站 iomap 输入区
    │ 快照 / 双缓冲
    ▼
控制算法
```

### 1.3 配置、状态与时间三条并行链路

数据链之外还有三条极易被忽略的链路：

- **配置链**：ESI/SII → SM/FMMU/PDO 映射 → 寄存器写入。
- **状态链**：主站写 `AL_CONTROL` → 从站 ESC/协议栈/应用处理 →
  `AL_STATUS_CODE` 与 `AL_STATUS`。
- **时间链**：主站周期调度 → NIC 收发 → 线路传播 → ESC 本地时钟 →
  PDI/应用 → 输出。DC 只同步特定时间基准，不会自动让应用代码变成实时代码。

### 1.4 一个输出字节的九层定位表

| 层 | 字节或状态在哪里 | 主站可直接观察什么 | 典型失败表现 |
|---|---|---|---|
| 应用 | `iomap[offset]` | 代码、日志、断言 | 主站从未写入，或写错位置 |
| PDO 映射 | 逻辑地址 + PDO 位宽 | ESI、PDO mapping、iomap 视图 | 相邻字段错位、位掩码错误 |
| 帧 | Data 区 + WKC | 十六进制帧、抓包 | PDU 长度、偏移或期望 WKC 错 |
| 链路 | 在途数据报与实际发送帧 | `DatagramState`、超时、重试 | `LOST`、`SEND_ERROR` |
| ESC 网络侧 | 端口收发的帧 | WKC、链路与错误计数 | 从站掉线、端口错误 |
| FMMU/SM | 逻辑到物理映射、方向与边界 | WKC、SM 状态、配置回读 | WKC 错误、拒绝写、状态机报错 |
| PDI | SPI 事务或 MCU memory load | SPI 波形、MCU 内存窗口 | 超时、busy、读回全 0/全 F |
| 从站协议栈 | PDO 缓冲区与 OD 别名 | 固件日志、断点、变量 | 映射成功但业务字段错 |
| 设备应用 | GPIO/PWM/DAC 与驱动器 | 示波器、LED、传感器、设备状态 | 总线正常但物理动作不发生 |

这张表应当成为所有故障分析的共同语言。判断顺序通常是从前向后缩小范围，
但“WKC 正常”后应直接检查 PDI 和从站应用，而不是继续怀疑主站帧编码。

### 1.5 四类故障不要混为一谈

1. **没有传输**：没有从站、链路中断、帧丢失、socket 错误。
2. **状态拒绝**：邮箱配置不合法、PDO 配置不合法、看门狗超时、应用未确认输出。
3. **传了但字节含义不对**：FMMU、SM、PDO、OD、ESI/SII 不一致。
4. **传对了但没有执行**：PDI 失败、固件没有更新缓存、设备应用未消费、硬件未供电。

“WKC 错”和“物理输出不动”不是同一类问题；把它们都归因于主站协议栈，
会浪费大量定位时间。

### 2.3 最小可工作知识集

如果时间非常有限，先学下面五项：

1. ESC 的寄存器、SM、FMMU 与 DPRAM。

## 3. 嵌入式基础：主站工程师需要掌握到什么程度

### 3.1 MCU、SoC 与内存映射外设

不要把 MCU 看成“更小的 CPU”。从主站视角，至少要理解：

- CPU、Flash、SRAM、外设通过片上总线/互连连接。
- 外设通常表现为一组带地址的寄存器；访问顺序和副作用可能重要。
- 寄存器类型可能是只读、只写、读清、写 1 清零、锁存或需要密钥序列。
- 复位和时钟必须先正确初始化，外设才有预期行为。
- 中断控制器决定中断优先级、屏蔽、挂起和清除。
- 固件运行依赖启动文件、链接脚本、栈、堆和中断向量表。
- 交叉编译产生的二进制必须通过调试器、DFU、OpenOCD 或厂商工具烧写。

主站工程师不需要手写启动代码，但需要能解释以下现象：

- 同一份协议代码在 x86 Linux 正常，在 MCU 上因对齐或栈大小失败。
- 状态读取得到全 `0xFF`，原因可能是 SPI 未初始化，而不是协议字段如此。
- 调试器暂停后主站超时，说明实时性和调试方式互相影响。
- 固件版本、板卡版本和 EEPROM 内容不同，行为也不同。

KickCAT 的两个典型 PDI 入口正好展示了两种访问模型：

- [`Lan9252.h`](../KickCAT/lib/slave/include/kickcat/ESC/Lan9252.h)：
  MCU 通过 SPI 间接访问外部 ESC。
- [`XMC4800.h`](../KickCAT/lib/slave/include/kickcat/ESC/XMC4800.h)：
  MCU 通过 `0x54010000-0x5401FFFF` 内存窗口访问集成 ESC。

两者在 `AbstractESC` 之上有相似的 `read/write` 接口，但底层延迟、原子性、
缓存语义和错误路径完全不同。抽象接口统一的是**协议语义**，不是硬件时序。

#### 自检

- 能解释 `.text`、`.data`、`.bss`、stack、heap 的区别。
- 能说明为什么读取一个硬件寄存器不能假定“读多少次都得到同一结果”。
- 能在链接 map 文件中找到协议缓冲区与栈的大致位置。
- 能解释调试器断点为什么会改变实时系统的行为。

### 3.2 四类地址不要混淆

| 地址 | 典型归属 | 作用 | 错误表现 |
|---|---|---|---|
| 主机虚拟地址 | 主站进程 | 访问 `iomap`、对象、队列 | 指针失效、生命周期错误 |
| EtherCAT 逻辑地址 | 数据报/FMMU | 一帧同时映射多个从站 | 偏移或 WKC 错误 |
| ESC 内部地址 | ESC DPRAM/寄存器 | SM 缓冲区、AL 状态、DC | 读写到错误寄存器 |
| MCU 物理地址 | SoC/外设窗口 | 通过 PDI 或内存映射访问 ESC | 地址越界、cache 不一致 |

再看一个实际例子：

1. 主站应用持有 `iomap.data() + offset`。
2. `Bus` 把该区间对应的逻辑地址写进数据报。
3. 从站 FMMU 把逻辑地址映射到 ESC 内部物理地址。
4. 从站 PDO 配置知道该物理区属于哪一个输出 SM。
5. `Lan9252::write/read` 通过 SPI 命令访问该 ESC 地址；
   `XMC4800::write/read` 则把 ESC 地址加上芯片窗口基址。
6. 从站应用最终看到的是自己的 `buffer_out` 或 `buffer_in`，而不是主站指针。

任何一层都可能“地址数值相同、对象不同”。例如 `0x1000` 在主站是 iomap
偏移，在 ESC 里可能是邮箱起始地址，在 MCU 上又可能属于另一块 SRAM。

#### 实验

选择一条最小 PDO，打印或记录：

```text
主站 iomap 偏移
PDU 逻辑地址
从站 SM 起始地址和长度
FMMU 逻辑起点和物理起点
从站 PDO 缓冲区地址
设备应用绑定对象的地址
```

不要只看数值是否“差不多”，要写出每个数值所属的地址空间。

### 3.3 字节序、对齐、位偏移与 C++ 对象表示

EtherCAT PDU 中的多字节字段按小端解释；Ethernet 帧自身的 EtherType 等字段
仍遵循 Ethernet 的字节序规则。KickCAT 当前明确按小端主机设计，但这并不意味着
可以随意把线上字节 `reinterpret_cast` 成 C++ 结构体。

必须掌握的概念：

- **字节序**：字节序列到整数的解释方式。
- **位序**：映射条目中的 bit offset、bit length 和字节内位布局。
- **对齐**：访问 `uint32_t*` 时地址可能必须满足对齐要求。
- **填充**：普通结构体可能插入 padding，线上布局通常不允许 padding。
- **别名规则**：用不兼容指针类型访问对象可能触发未定义行为。
- **符号扩展**：有符号小宽度字段提升到更大整数时的变化。
- **越界**：最后一个字段是否占满字节、最后一个 bit 是否跨字节。

推荐的读法：

```cpp
uint16_t read_le16(uint8_t const* p)
{
    return static_cast<uint16_t>(p[0])
         | (static_cast<uint16_t>(p[1]) << 8);
}
```

写外部字节时同理，逐字节编码是最容易审查的方式。若必须使用结构体，应至少：

```cpp
static_assert(sizeof(WireHeader) == 10);
static_assert(offsetof(WireHeader, payload_length) == 6);
```

并确认编译器对 packed/unaligned 访问的行为。KickCAT 的部分硬件控制结构使用了
`__attribute__((__packed__))`，但编译器扩展、未对齐访问代价和可移植性仍需
单独评估。工程规则是：

> 外部字节流与内部 C++ 对象之间要有**显式序列化/反序列化边界**，
> 不要靠“结构体看起来一样”建立边界。

PDO 还多了位级复杂度。一个 3 bit 字段、一个跨字节的 12 bit 字段和一个 1 bit
标志，不能用三个独立字节简单代替。至少应验证：

- `bit_offset + bit_length` 不越界。
- SM 长度是否等于所有映射项按位累加后的向上取整字节数。
- 写回时是否正确保留同一字节中的相邻字段。
- ESI、主站映射视图和从站 OD 的位宽是否一致。

### 3.4 cache、DMA、`volatile`、原子操作和内存屏障

这五个词经常被混用，但它们解决不同问题：

| 机制 | 解决的问题 | 不解决的问题 |
|---|---|---|
| `volatile` | 每次访问都生成可观察的读写，常用于 MMIO | 线程同步、原子性、cache 一致性 |
| `std::atomic` | 对特定对象的原子访问和内存序 | 多字段一致性、硬件 DMA 所有权 |
| memory barrier/fence | 限制编译器或 CPU 的重排 | 自动刷新数据 cache |
| cache flush/invalidate | 让 CPU cache 与共享内存/DMA 一致 | 多生产者协议的正确性 |
| mutex/队列 | 保护复合不变量、传递数据所有权 | 实时延迟上界，除非可证明 |

主站进程通常至少有这些执行者：

- 控制周期线程；
- 网络收发线程/内核中断；
- 邮箱处理线程；
- 诊断、日志或 UI 线程；
- 从站侧的 PDI 执行者和设备应用。

一个 8 字节 PDO 在 32 位系统上可能被分多次写入。如果控制线程读取时恰好和
接收线程更新重叠，就可能读到“半旧半新”的数据。解决方案应根据需求选择：

- 单生产者单消费者双缓冲，用原子索引发布完整快照；
- 在实时线程中交换两个预分配缓冲区的所有权；
- 对复合数据使用有界锁，并测量最坏持锁时间；
- 保证同一方向只有一个写者，再从协议层简化问题。

不要写一个“看起来更快”的无锁结构而没有压力测试。无锁只表示没有阻塞，
不表示没有数据竞争、ABA、内存序错误或活锁。

#### MMIO 与 DMA 检查表

- 访问硬件寄存器是否需要 `volatile`？
- 读操作是否会清除硬件事件？
- 写寄存器后是否需要读回或插入屏障？
- DMA 缓冲是否按 cache line 对齐？
- DMA 前是否 flush，完成后是否 invalidate？
- 设备是否仍拥有缓冲区时就被 CPU 复用？
- 声明的“无锁”是否存在多个写者或非原子复合状态？

### 3.5 中断、轮询和下半部处理

中断带来低延迟，但也带来并发、优先级和抖动。必须理解：

- 中断延迟 = 硬件识别 + 屏蔽时间 + 更高优先级中断 + 上下文切换。
- ISR 应尽量短：记录时间戳、清除源、把数据放入队列、唤醒任务。
- 不应在 ISR 中做 SPI 大块传输、动态分配、阻塞等待、复杂日志或异常处理。
- 中断合并/coalescing 降低 CPU 占用，却可能增加单次响应延迟。
- 轮询提高可控性，但占用 CPU，且轮询周期本身成为抖动来源。
- 事件寄存器可能要求“先读状态、再写 1 清除”，顺序错误会丢事件。

从站侧常见事件源包括：

- ESC 收到邮箱数据；
- 过程数据看门狗状态变化；
- DC SYNC0/SYNC1 到达；
- PDI 事件或 SM 状态变化；
- 网络链路/端口事件。

当前 KickCAT 仿真器不模拟中断，所以仿真通过不能证明以下行为：

- IRQ 极性、屏蔽、清标志和共享中断正确；
- ISR 与主循环之间的数据竞争正确；
- 中断延迟和抖动满足要求；
- 事件丢失后能恢复。

LAN9252 初始化中的 `pollRegister()` 是轮询式 PDI 的典型例子。它先读状态，再
判断 ready/busy；生产代码应使用单调时钟设置明确 deadline，而不是只依赖一个
与 CPU 频率、SPI 速度相关的循环次数。

### 3.6 SPI 与 LAN9252 PDI

SPI 不是“调一个 `read()` 就从外部芯片取到数据”。至少要掌握：

- SCLK、MOSI、MISO、CS 四根信号；
- CPOL/CPHA 对应的 SPI mode；
- 片选建立/保持时间；
- 全双工：发送命令的同时可能收到旧数据；
- 时钟频率、线长、负载和信号完整性；
- 每次事务固定开销，小块随机访问可能很慢；
- 多任务共享 SPI 总线时的事务互斥；
- 设备 ready/busy 与超时，而不是固定延时“应该够了”。

阅读
[`Lan9252.cc`](../KickCAT/lib/slave/src/ESC/Lan9252.cc) 时，可按下面链条理解：

1. 通过 `BYTE_TEST` 检查 SPI 数据路径，期望固定测试值。
2. 写 `RESET_CTL`，等待复位完成。
3. 检查 `HW_CFG` 的 `DEVICE_READY`。
4. 小地址寄存器通过 `ECAT_CSR_CMD`/`ECAT_CSR_DATA` 间接访问。
5. 过程 RAM 通过 PRAM 读/写命令与 FIFO 数据窗口访问。
6. 每次命令后检查 busy，部分路径等待 FIFO 槽位。
7. 端口层返回成功字节数或负 errno，上层再决定重试/报错。

源码里还有一个对主站工程师很有价值的观察：

- CSR 命令有 `ECAT_CSR_BUSY` 和约 10 ms 的 `TIMEOUT`；
- PRAM 读路径有超时；
- 当前 PRAM 写路径在等待 FIFO 槽位时没有显式 elapsed-time 超时。

这不是让你马上改成“永不失败”，而是提醒你做硬件优化/移植时检查所有有界循环：

```text
每个 while 是否有退出条件？
退出条件是否包含取消、超时和错误状态？
超时依据是单调时间还是循环次数？
超时后是否恢复设备到可重试状态？
失败是否会继续锁住 SPI 总线？
```

#### SPI 调试证据

使用逻辑分析仪时，不要只看“有没有时钟”。应同时解码：

- CS 是否在完整命令期间保持有效；
- 命令、地址、数据在哪个时钟边沿采样；
- MISO 是否出现 expected `BYTE_TEST`；
- busy 位何时变化；
- 两次事务之间是否留出设备处理时间；
- 异常帧前后是否出现重试或超时。

### 3.7 RTOS、调度和实时性

实时不等于“运行快”，而是**在确定的截止时间内完成**。NuttX、Linux
RT-PREEMPT 以及其他 RTOS 都需要同样的分析方式。

必须理解：

- 任务状态：运行、就绪、阻塞、挂起；
- 抢占式调度与优先级；
- tick、高分辨率定时器和单调时钟；
- 信号量、消息队列、事件组；
- 临界区、中断屏蔽和关调度；
- 栈大小、栈溢出和高水位；
- 优先级反转与优先级继承；
- 动态内存分配、页错误和不可预测的 I/O；
- WCET（最坏执行时间）、抖动和尾延迟。

一个典型从站主循环可能包含：

1. 读取或等待 ESC 事件；
2. 处理邮箱；
3. 执行 ESM；
4. 把输出缓冲区交给设备应用；
5. 更新输入缓冲区；
6. 维护诊断与看门狗。

当前 KickCAT 示例中的 `while (true) { slave.routine(); ... }` 是开发参考，
不是对所有设备应用都成立的实时调度方案。实际产品要把下列工作区分开：

- 硬截止时间工作：SYNC0 后的输出更新、控制闭环、看门狗喂狗；
- 软实时工作：诊断采样、非关键状态显示；
- 后台工作：日志上传、FoE、参数备份。

不要用高优先级线程包住所有工作。高优先级任务做过长，
低优先级邮箱和诊断就会饥饿；反过来，邮箱线程抢占周期线程会产生周期抖动。

#### 周期循环的最低要求

- 使用绝对截止时间，避免 `sleep(period)` 的累计漂移。
- 记录每周期开始、发送、接收和完成的单调时间戳。
- 统计 p50、p99、max，而不是只看平均值。
- 周期路径不执行堆分配、文件 I/O、终端输出和不可控锁等待。
- 所有错误路径有上限，能进入安全状态并保留第一现场。
- 对关键共享数据使用快照或明确的同步协议。
- 在目标硬件、目标内核、目标网络配置下测量，不用开发机代替。

### 3.8 看门狗不是一个软件变量

至少区分四层：

1. **ESC PDI 看门狗**：MCU 长时间不访问 ESC 时触发。
2. **ESC 过程数据看门狗**：主站长时间没有有效过程数据访问时触发。
3. **主站通信超时**：某个帧、邮箱或状态迁移没有在期限内完成。
4. **MCU/SoC 硬件看门狗**：固件卡死或调度失效时复位设备。

KickCAT `Bus::resetSlaves()` 会配置 PDI/PDO 看门狗；从站 ESM 读取
`WDOG_STATUS`，OP 状态检测到过程数据看门狗超时后回到 SAFE_OP 并报告
`SYNC_MANAGER_WATCHDOG`。

主站设计要回答：

- 超时阈值相对于周期、最大抖动和网络异常留了多少余量？
- 超时后从站进入什么安全状态？输出是否会保持残余值？
- 恢复后是自动重新进入 OP，还是要求应用显式确认？
- 上游控制器的超时和 ESC 看门狗是否构成合理的时间层次？
- 设备是否有独立的硬件急停/安全扭矩关闭，而不是依赖 PDO？

看门狗太长会让故障反应变慢，太短会因正常抖动误触发。只能通过故障注入和
目标系统测量确定，不能凭“通常是三个周期”直接部署。

### 3.9 C++ 在固件和主站中的工程约束

纯软件 C++ 经验很有价值，但需要补三条工程纪律：

1. **控制面可以有动态内存，周期数据面应尽量没有。**
   映射配置阶段创建 vector、字典和邮箱对象可以接受；每周期重新分配
   `std::vector`、格式化字符串或构造异常对象会制造延迟尖峰。
2. **所有权和生命周期必须能画出来。**
   KickCAT 从站对象大量使用非拥有指针，`CoE::Dictionary`、PDO 缓冲区、
   邮箱和 `slave::Slave` 之间必须由应用保证生命周期。
3. **错误模型要适合嵌入式。**
   底层驱动常用返回负 errno，上层再翻译成协议错误或诊断；异常可用于
   控制面，但不要在 ISR 或硬实时数据路径中依赖异常展开。

建议的 C++ 审查项：

- 外部数据读取是否经过显式编码/解码？
- `reinterpret_cast` 是否伴随对齐与别名论证？
- 结构体是否有 `static_assert` 和边界检查？
- 实时路径是否可能分配、抛异常、阻塞或写日志？
- 共享数据的写者和读者各是谁？
- 硬件对象析构时是否仍在被 ISR/任务使用？
- 整数宽度是否使用 `uint16_t`/`uint32_t` 固定宽度类型？
- 位掩码是否避免有符号移位和未定义行为？

### 3.10 数字 IO 与电气边界

主站工程师不需要设计板卡，但必须能安全连接和验证测试 IO。至少掌握：

- 3.3 V、5 V、24 V 等电压域，以及输入高/低门限，不能只看“额定电压”。
- 源型（sourcing）和漏型（sinking）输入/输出，灌电流与拉电流。
- 开集/开漏输出需要上拉或外部负载，不能悬空推断电平。
- 未连接或浮空输入可能抖动，软件看到的值不代表真实电气状态。
- 感性负载需要续流/保护，输出额定电流和浪涌不能忽略。
- 共地、隔离电源、地环路、共模范围以及逻辑分析仪参考地。
- 上电/断电顺序、热插拔、反接和短路保护。
- 24 V 工业 IO 的隔离、ESD/浪涌和 EMC 处理由硬件团队负责，但软件人员必须
  知道这些因素会产生间歇性错误。

功能安全边界尤其重要：

- 普通 EtherCAT PDO 和看门狗不能替代硬件急停、安全继电器或 STO。
- 不要把“主站发出 OFF 命令”当成唯一停机能量的手段。
- 驱动器的使能、故障复位、STO 和保持制动必须按设备手册设计。
- 软件测试输出应从 LED、低电压、小电流负载开始，确认接线后再接执行器。

主站工程师的及格线是：能读原理图上的电压域、IO 类型、参考地和保护器件，
在接线前发现明显错误；PCB 叠层、EMC 整改和隔离电源设计可以交给硬件团队。

## 4. ESC 与从站：从“黑盒”变成可解释系统

### 4.1 ESC 的四个域

```text
──────────────────────────── EtherCAT 网络侧 ────────────────────────────
端口 0/1/2/3 ──► 帧解析 ──► 地址匹配 ──► 读/写 ──► 继续转发 ──► WKC
                               │
                               ├── FMMU：逻辑地址 → ESC 物理地址
                               │
─────────────────────────── ESC 内部资源 ───────────────────────────────
寄存器 / DPRAM / SyncManager / FMMU / EEPROM / DC / 错误计数
                               │
────────────────────────────── PDI ─────────────────────────────────────
SPI / 内存映射 / 并行接口 / 数字 IO
                               │
────────────────────────── 从站协议栈与设备应用 ─────────────────────────
ESM / 邮箱 / CoE / PDO / 对象字典 / 运动或 IO 应用
```

主站工程师应能区分：

- **ESC 网络侧**出了什么问题；
- **ESC 内部映射/状态**出了什么问题；
- **PDI** 出了什么问题；
- **从站软件**或设备应用出了什么问题。

### 4.2 FMMU、SyncManager、PDO 不是同义词

| 机制 | 主要职责 | 不负责什么 | 观察证据 |
|---|---|---|---|
| FMMU | 逻辑地址与 ESC 物理内存之间的位/字节映射 | 邮箱协议、对象含义、应用执行 | 逻辑访问是否命中、WKC、配置回读 |
| SyncManager | 规定一段 ESC 缓冲区的方向、长度、访问与同步语义 | 对外部字段做语义解释 | SM valid、状态/事件、缓冲区读写是否被接受 |
| PDO | 对象字典中的字段如何组成输入/输出过程数据 | 直接完成帧地址转换 | mapping、bit length、iomap 布局 |
| OD | 从站对象的索引、子索引、类型、访问权限和值 | 自动保证 ESI/SII 与固件一致 | SDO 读写、固件 OD 内容 |
| ESI/SII | 配置和设备介绍信息 | 运行时代码本身的执行 | 主站解析出的设备/邮箱/PDO 信息 |

一个便于记忆的比喻：

- FMMU 像地址翻译表；
- SM 像带方向和访问规则的邮箱/货运站；
- PDO 像货物清单和字段布局；
- OD 像设备属性目录；
- ESI/SII 像设备说明书与出厂配置卡。

比喻只能帮助入门，不能替代寄存器行为。例如 FMMU 配置成功不等于 PDO 映射正确；
SM 有效也不等于对象字典中的字段类型正确。

### 4.3 典型 SM 角色

常见从站布局是：

- SM0：接收邮箱；
- SM1：发送邮箱；
- SM2：输出过程数据；
- SM3：输入过程数据。

但不要把这个编号当成普适常量。应从 ESI/SII 和 ESC 配置读取实际布局。
KickCAT 当前每方向只支持一个 PDO SyncManager；对于某些无邮箱终端，
过程数据甚至可能出现在 SM0/SM1。

`in/out` 的视角也容易混淆：

- 主站视角的“输出”通常是写入从站设备的方向；
- 邮箱的 “in/out” 取决于看 ESC 还是看主站。

阅读代码时始终问：“这是以哪个设备为观察者的方向？”并在笔记里写明。

### 4.4 ESM：从站并不是被动执行主站“设置状态”

主站通过写 `AL_CONTROL` **请求**目标状态。从站侧 ESC/协议栈/应用检查邮箱、
PDO、看门狗和输出有效性，再写 `AL_STATUS` 与 `AL_STATUS_CODE`。主站写请求成功，
不代表从站接受。

工程上应把五个状态理解为不同能力集合：

| 状态 | 重点能力 | 主站常见动作 | 主站应观察 |
|---|---|---|---|
| INIT | 基础寄存器/配置，邮箱和过程数据未正常启用 | 复位、地址、基础配置 | 是否回到 INIT、DL 状态 |
| PRE_OP | 邮箱可用，过程数据映射配置 | SDO、CoE、PDO 配置 | 邮箱 SM 是否有效、AL 错误码 |
| SAFE_OP | 输入可用；输出可交换，但必须经过应用验证和安全策略 | 检查映射、试写安全输出 | PDO 配置错误、看门狗、输出确认 |
| OP | 正常周期交换 | 周期 PDO、诊断、DC | WKC、看门狗、AL 状态 |
| BOOT | 固件升级邮箱布局 | FoE 等启动态操作 | Bootstrap 邮箱配置 |

从站进入 SAFE_OP/OP 的典型检查包括：

- 邮箱配置是否仍然有效；
- PDO SM 是否存在、长度和激活状态是否正确；
- 输入/输出映射是否与对象字典和 SM 长度一致；
- 应用是否确认输出数据有效；
- 过程数据看门狗是否超时。

KickCAT 的 ESM 实现位于：

- [`ESM.cc`](../KickCAT/lib/slave/src/ESM.cc)；
- [`ESMStates.cc`](../KickCAT/lib/slave/src/ESMStates.cc)。

`ESM::StateMachine::play()` 先读 `AL_CONTROL` 和 `WDOG_STATUS`，执行当前状态，
发生迁移时更新状态；上报错误时先写 `AL_STATUS_CODE`，再写 `AL_STATUS`。
这个顺序很重要：主站应先读 Status Code 和 Status，避免看到新状态但仍是旧错误原因。

有输出 PDO 时，从站应用在 SAFE_OP 收到有效输出后必须调用
`validateOutputData()`，否则不能进入 OP。LAN9252 参考示例用本地 `bound`
锁存保证一个主站会话只确认一次，避免看门狗回落后反复重新进入 OP。

主站侧诊断不要只调用“等待达到 OP”然后超时。至少记录：

```text
请求前的状态
请求的目标状态
AL_STATUS
AL_STATUS_CODE
WDOG_STATUS
邮箱/SM 配置结果
最后一个成功的周期 WKC
```

### 4.5 邮箱与 PDO 是两套通信模型

| 维度 | PDO | 邮箱 |
|---|---|---|
| 主要用途 | 周期过程数据 | 参数、对象访问、诊断、固件 |
| 典型时延 | 一个或数个周期 | 多轮轮询，可能毫秒到秒 |
| 数据量 | 小、固定布局 | 通常更大、可变长度 |
| 失败表现 | WKC 错、状态回落、数据陈旧 | 邮箱满/空、toggle、超时、SDO abort |
| 主站路径 | `Bus::buildFrames`、周期回调 | `Mailbox`、`CoE`、`pending`/`to_send` |
| 从站路径 | PDO 更新与 OD 别名 | 邮箱 receive/process/send |

ESC 的邮箱通常是带状态标志的同步缓冲区，不是一个可以无限追加的队列。
主站软件里的 `to_send`、`to_process` 等容器才提供了队列/调度层。

从站 `slave::Slave::routine()` 当前先执行邮箱
`receive → process → send`，再执行 ESM `play()`。这形成一个协作式推进模型：
邮箱服务不会自动脱离状态检查，状态迁移也不会假设邮箱已经清空。阅读源码时可以
把它抽象为：

```text
选择当前状态使用的邮箱
  → 读取请求
  → 分发并构造应答
  → 写回应答
  → 处理主站请求的状态迁移
  → 更新 AL Status
```

仿真中一个主站周期推进一次 `routine()`；真实系统可能由不同任务/中断驱动，
因此要重新检查优先级和共享数据。

### 4.6 ESI、SII、固件 OD 和 PDO 的一致性

一个从站设备至少有四个相关事实来源：

| 来源 | 负责什么 | 典型不一致 |
|---|---|---|
| ESI XML | 工程配置里的设备/对象/PDO 描述 | 版本旧、映射改了但 XML 没更新 |
| SII/EEPROM | 主站启动早期能读到的厂商、SM、邮箱等信息 | 邮箱大小或 PDO 类别与固件不一致 |
| 固件对象字典 | 运行时 SDO 看到的真实对象 | 类型、访问权限或默认值不同 |
| PDO 映射 | 实际字段到过程缓冲区的 bit 布局 | 长度、偏移、buffer 大小不匹配 |

一致性检查应覆盖：

- Vendor ID、Product Code、Revision、Serial；
- 标准/启动态邮箱起始地址和大小；
- 每个 PDO SM 的方向、长度和激活方式；
- `0x1C10 + SM index` 分配对象；
- PDO mapping 中每个 index/subindex/bit length；
- 输入/输出缓冲区容量；
- 对象字典字段类型与位宽；
- iomap 偏移是否按设备顺序正确累加。

KickCAT `PDO::configureMapping()` 会：

1. 找到 PDO SM；
2. 读取 `0x1C10 + SM index` 分配对象；
3. 解析 `0x1600/0x1A00` 一类映射对象；
4. 检查 index、subindex、bit length；
5. 检查总位数向上取整后是否等于 SM 长度；
6. 在提交前验证输入和输出两个方向；
7. 把对象字典条目的 `data` 别名到过程缓冲区。

这说明“SDO 能读到对象”与“PDO 能正确交换”是两件事。SDO 成功只证明对象存在；
PDO 还要求分配、映射、bit 布局和 SM 长度完全一致。

### 4.7 WKC 的正确含义与盲区

WKC 是工作计数器，反映数据报在 ESC/FMMU/SM 上产生了多少次预期访问。它不能证明：

- PDO 字段类型是对的；
- 从站应用消费了输出；
- 执行器已动作；
- 数据在应用时间尺度上新鲜；
- 看门狗没有即将超时；
- DC 已同步。

测试时应同时记录：

- 期望 WKC 与实际 WKC；
- 数据报所属从站/逻辑区；
- SM 状态和 AL 状态；
- 同一时刻的设备应用缓冲区；
- 采样时间戳。

只有这样，才能区分“FMMU 没命中”和“命中后业务字段仍然错”。

### 4.8 分布式时钟 DC

从 ESC 视角，DC 至少包括：

- 本地系统时间；
- 参考时钟选择；
- 帧接收时间戳；
- 传播延时；
- 系统时间偏移与漂移补偿；
- SYNC0/SYNC1 事件；
- 锁相与保持。

从主站视角，DC 的目的是让多个从站的采样/执行在共同时间基准附近发生。
它不能替代：

- 主站线程的实时调度；
- PDI 和从站应用的执行延迟；
- 输出硬件本身的建立时间；
- 网络丢帧后的恢复策略。

KickCAT 当前状态必须特别记住：

- 仿真器有 DC 时钟、漂移和 SYNC0 模型；
- 主站 DC 仍是实验性功能；
- 真实从站侧 DC 尚未实现；
- 仿真通过不能证明真实 ESC 的锁相、传播延时和中断行为正确。

做运动控制或高速同步 IO 前，必须把 DC 当作独立工程问题验证，而不是打开
一个布尔开关就宣布同步完成。

### 4.9 仿真 ESC 与真实 ESC 的差异

| 维度 | 仿真 ESC | 真实 ESC/硬件 |
|---|---|---|
| 寄存器访问 | 普通函数调用 | SPI/内存映射，可能有等待、竞争和错误 |
| 时序 | 可确定推进 | PHY、中断、总线、调度共同引入抖动 |
| EEPROM/SII | 文件/内存模型 | 烧写、校验、版本和损坏问题 |
| 中断 | 不模拟 | IRQ 极性、清除、共享、优先级均需验证 |
| DMA/cache | 不涉及 | ownership、屏障、cache 一致性 |
| 端口/PHY | 拓扑路由模型 | link、线缆、EMC、端口错误计数 |
| 看门狗 | 软件推进 | 时钟精度、硬件行为和恢复状态 |
| DC | 软件时钟模型 | 硬件时间戳、SYNC 信号、锁相 |

这张表是“仿真正常、硬件失败”时最应该先看的清单。

## 5. 主站侧：Linux、网络与实时工程

### 5.1 一个周期的时间去哪里了

```text
应用计算
  + iomap 快照/控制输出
  + 构造/复用帧
  + socket send/recv 系统调用和驱动排队
  + NIC 发送
  + 电缆/PHY/ESC 转发
  + 从站 PDI 与设备应用
  + NIC 接收与中断/轮询
  + 主站分发和回调
  = 端到端响应
```

这里任何一个平均值都不能代表最大值。实时系统至少记录：

- 周期开始到发送的延迟；
- 发送到收到完整回环的延迟；
- 收到到应用读取 iomap 的延迟；
- 每个周期的实际开始间隔；
- 重试、丢帧、WKC 错和状态恢复次数；
- 邮箱活动对周期抖动的影响。

### 5.2 Linux 实时调优的边界

KickCAT 的
[`PERFORMANCE.md`](../KickCAT/docs/PERFORMANCE.md)
给出了 RT-PREEMPT、`chrt`、CPU 隔离、NIC IRQ 优先级和 AF_XDP 的实践入口。
学习时应理解每项的目的，而不是盲目复制所有命令：

- RT-PREEMPT 降低内核不可抢占段带来的尾延迟；
- `SCHED_FIFO` 提高周期线程优先级，但错误的高优先级忙等会锁死系统；
- CPU 隔离减少无关任务干扰，仍不能消除内存、总线和设备抖动；
- 调整 IRQ 优先级可以减少网络唤醒延迟；
- 禁用中断合并改善单帧响应，但可能增加 CPU 负载；
- 关闭 RT throttling 是高风险管理操作，只能在受控设备上验证；
- AF_XDP 绕过大部分内核网络栈，降低延迟但增加部署和权限复杂度。

Windows 当前定位是工具和测试平台，不是硬实时主站。不要用“Windows 定时器
可以设到 1 ms”推导 EtherCAT 周期可稳定达到 1 ms。

### 5.3 原始以太网、网卡和 PHY

EtherCAT 使用原始 Ethernet 帧，常用 EtherType `0x88A4`，不走 IP/UDP。
因此：

- Wireshark 过滤条件是 `ether proto 0x88a4`，不是 TCP/UDP 端口。
- 主站需要原始帧访问权限；Linux 常见能力为 `CAP_NET_RAW`，
  AF_XDP 还需要更多网络能力。
- 应使用专用有线网口和稳定驱动，避免无线、USB 转接、虚拟网桥的额外抖动。
- 即使没有 IP 地址，NIC/PHY 仍必须 link up；不要只看 `ping` 是否成功。
- 需要关注速度、双工、CRC/错误计数、IRQ 分布、中断合并和驱动日志。
- 普通交换网络中的其他广播、流量控制和动态拓扑可能干扰控制网段。

Linux 默认 socket 后端便于开发。AF_XDP 适合需要更低延迟和更可控接收路径的
部署，但它不会自动修复映射错误、从站固件或调度设计。

### 5.4 线程和任务划分

一个可维护的主站通常把工作分层：

| 工作 | 时间要求 | 设计建议 |
|---|---|---|
| 周期过程数据 | 硬截止时间 | 固定缓冲、无分配、最短锁、绝对时间调度 |
| 网络收帧/错误处理 | 高优先级 | 只做解析、入队和唤醒，必要时预分配 |
| 状态迁移/邮箱 | 软实时 | 与周期线程解耦，设置独立超时 |
| 诊断/日志 | 可延迟 | 有界环形缓冲，后台落盘 |
| UI/配置 | 非实时 | 不进入周期线程，发布只读快照 |

锁的设计要能回答最坏持锁时间。一个“平均 1 微秒”的 mutex 对于 500 微秒周期
仍可能制造不可接受的尾延迟，尤其是另一个线程持锁时发生页错误或 I/O。

### 5.5 测量与验收

一个主站试验至少应产出以下测量表：

| 指标 | 采样方式 | 为什么需要 |
|---|---|---|
| 周期间隔 | 单调时钟时间戳 | 判断调度抖动 |
| 发送完成时间 | `send` 前后时间戳 | 区分应用与内核/驱动延迟 |
| 回环时间 | 发送到完整收帧 | 定位网络/从站链延迟 |
| WKC 异常率 | 每帧回调 | 判断映射、掉线和干扰 |
| 状态切换耗时 | AL Control/Status 时间戳 | 判断 ESM/邮箱问题 |
| SDO 延迟 | 请求到响应 | 判断邮箱吞吐和从站处理 |
| DC 偏移/SYNC 缺失 | DC 寄存器/波形 | 判断同步质量 |
| CPU/IRQ 分布 | `perf`、`/proc/interrupts`、ftrace | 发现系统干扰 |

验收应写清 p99、max、持续时间和故障场景。只在空闲机器上运行 10 秒，
不能证明生产实时性。

## 6. 从现象到证据：主站故障定位手册

### 6.1 五分钟分诊

1. **先安全停下**：断开执行器或关闭驱动使能，保留日志和现场。
2. **确认物理链路**：供电、线缆、link、接口名、PHY 速度/双工。
3. **确认能枚举**：BRD/APRD 一类基础读是否返回、WKC 是否符合拓扑。
4. **确认 SII/邮箱**：能否在 PRE_OP 读到设备信息和邮箱配置。
5. **确认状态迁移**：请求前后的 AL Status、Status Code、WDOG_STATUS。
6. **确认过程映射**：FMMU、SM、PDO、iomap、帧偏移和期望 WKC。
7. **确认从站执行**：PDI 缓冲区、固件变量、GPIO/PWM、设备状态。
8. **确认时间**：周期抖动、回环延迟、看门狗阈值、DC 状态。

故障定位的第一原则是：**先确定异常最早出现在哪一层，再修改代码。**

### 6.2 常见现象对照表

| 现象 | 第一检查 | 第二检查 | 不要先做什么 |
|---|---|---|---|
| 没有检测到从站 | 接口名、权限、link、供电 | `BRD(TYPE)` 是否收到、WKC 是多少 | 直接改 ESM 状态逻辑 |
| PRE_OP 超时 | SII/EEPROM、邮箱地址和大小 | `AL_STATUS_CODE`、SM 是否有效 | 把 PDO 映射错误当成邮箱错误 |
| 进 SAFE_OP 失败 | PDO SM 是否存在、长度/方向/激活 | `INVALID_*_CONFIGURATION` 错误码 | 盲目增加等待时间 |
| SAFE_OP → OP 超时 | 输出是否被应用验证 | 看门狗、AL Status、设备手册 | 反复重试掩盖状态拒绝 |
| WKC 间歇错误 | 拓扑、线缆、link、错误计数 | 逻辑地址、FMMU、帧是否过长 | 只看单次成功日志 |
| WKC 持续错误 | 期望贡献数量、映射、掉线从站 | 抓包核对 PDU 逻辑地址和长度 | 直接把 WKC 校验关掉 |
| SDO 超时 | 邮箱可读/可写、SM 状态 | counter/toggle、对象是否存在、分段传输 | 重发无限次 |
| 输入数据错位 | ESI/SII/OD 版本、PDO mapping | bit offset、SM 长度、iomap 偏移 | 用 `+1`/`-1` 猜字段 |
| 数据周期性跳动 | 双缓冲/快照、线程优先级 | 是否有半更新、cache/DMA、调度抖动 | 用 `volatile` 一把梭 |
| 看门狗反复触发 | 主站周期尾延迟、网络丢帧 | ESC watchdog、从站 PDI 访问 | 直接把看门狗调得很长 |
| DC/SYNC0 异常 | 参考时钟、DC 使能、传播延时 | 硬件时间戳和 SYNC 波形 | 用系统墙钟直接写 DC |
| 仿真正常实机失败 | PDI、PHY、EEPROM、固件版本 | 真实 ESC 的限制、中断/缓存 | 继续只跑仿真找答案 |

### 6.3 证据包

一次有价值的排障至少保留：

- 主站、内核、驱动、固件、板卡、EEPROM/ESI 版本；
- 拓扑和物理接线；
- 主站完整命令与关键日志；
- 帧的十六进制/抓包文件；
- iomap、FMMU、SM、PDO 映射表和偏移；
- `AL_STATUS`、`AL_STATUS_CODE`、`WDOG_STATUS`；
- 设备应用输入/输出缓冲区；
- 周期时间戳和抖动摘要；
- 为验证假设做的单变量改动；
- 结论、未验证项和复现步骤。

没有这些证据的“我认为是时序问题”无法复用，也无法交接。

## 7. 实验路线：无硬件先建模型，有硬件再验证物理层

### 7.1 无硬件实验

先运行主学习计划中的 `simulated_bus`，然后把每个实验落成一个可重复目录。

#### 实验 A：主站字节到软件 ESC 的完整链路

选一个输出字节和一个输入字节，记录：

```text
应用写入 iomap 的偏移
对应的逻辑地址/数据报偏移
从站 FMMU/SM 配置
EmulatedESC 中的物理地址
从站输出缓冲区
设备应用读取点
```

交付一张带源码路径和运行时值的链路图。

#### 实验 B：字节模式与位宽

使用 `0x00`、`0x01`、`0x80`、`0xFF` 和交替位模式，观察：

- 字段是否按预期位宽截断；
- 相邻输入/输出字段是否互相覆盖；
- 位偏移是否与 mapping 一致；
- iomap 的字节顺序是否与你的笔记一致。

#### 实验 C：制造映射长度不一致

让 PDO mapping 总位数与 SM 长度或缓冲区容量不一致，记录：

- 错误在哪里被检测；
- 是主站异常、从站 AL 错误，还是仅 WKC 变化；
- `AL_STATUS_CODE` 的前后值；
- 恢复时是否必须回到 INIT/PRE_OP。

不要只记“失败了”，要记“谁最先知道失败了”。

#### 实验 D：制造邮箱超时

让请求等待超过期限，观察邮箱 can-read/can-write、counter/toggle、pending
请求和最终超时。回答：

- 是邮箱不可用、对象不存在，还是普通轮询太慢？
- 重试是否会重复提交同一个请求？
- 超时后邮箱状态是否还被继续消费？

#### 实验 E：看门狗和安全状态

在仿真模型中制造过程数据中断，检查：

- 哪个状态在读 `WDOG_STATUS`；
- OP 会回到哪个状态；
- 从站应用何时清除输出验证；
- 恢复后如何重新进入 OP。

记录仿真器能模拟和不能模拟的硬件部分。

#### 实验 F：仿真器边界报告

写一页对照表，逐项列出本实验涉及的：

- 真实寄存器 vs 函数模型；
- 中断 vs 轮询；
- DMA/cache vs 普通内存；
- PHY/link vs 拓扑对象；
- 硬件时间戳 vs 软件时钟。

无硬件路线的验收重点不是“把仿真改得无所不能”，而是明确知道哪些结论
只能在实机上验证。

### 7.2 有硬件实验

#### 板卡选择

两个参考方向：

- **XMC4800 Relax Kit**：集成 ESC、内存映射访问，变量少，适合先建立
  “ESC/PDI/ESM/PDO”整体模型。
- **Freedom K64F + LAN9252**：外部 ESC、SPI PDI，适合学习 SPI 时序、
  busy/超时、逻辑分析仪和 PDI 调试。

若目标是系统理解且条件允许，顺序建议是：

```text
先 XMC4800 跑通最小闭环
  → 再 LAN9252 学习 SPI/PDI 细节
  → 最后做多从站、看门狗和故障注入
```

只有一块板也可以完成大部分主站学习；把另一条硬件路径写入“未验证清单”。

#### 安全第一

- 先只接 LED、低电压数字输入或不带负载的输出。
- 确认 IO 电压、灌/拉电流、共地和隔离边界。
- 不要用万用表表笔或逻辑分析仪探头随意跨接电源。
- 电机/执行器必须有独立硬件急停或安全扭矩关闭。
- 不把软件 PDO、看门狗或 PC 进程当作唯一安全保护。
- 不确认驱动器手册中的使能、故障复位和安全状态前，不运行高能量设备。

#### Bring-up 检查表

- [ ] 记录主站、固件、板卡、ESC、ESI/SII、工具链版本。
- [ ] 记录供电、接线、接口、PHY link 和从站拓扑。
- [ ] 确认固件烧写成功，串口/LED 能证明 MCU 在运行。
- [ ] 在 LAN9252 路径检查 `BYTE_TEST`、复位和 `DEVICE_READY`。
- [ ] 读取 ESC `TYPE`、Revision、SII/EEPROM 和邮箱信息。
- [ ] 用抓包确认 BRD/APRD 请求与回复、WKC 和拓扑位置。
- [ ] 单从站跑通 INIT → PRE_OP → SAFE_OP → OP。
- [ ] 先跑一个静态映射和一个输出，再启用动态映射。
- [ ] 用一个输入/输出字节验证字节序、位序和偏移。
- [ ] 记录 `AL_STATUS`、`AL_STATUS_CODE`、`WDOG_STATUS`。
- [ ] 人为断链/断电并验证恢复流程。
- [ ] 人为延迟主站周期并验证看门狗和从站安全状态。
- [ ] 记录周期 p50/p99/max、回环延迟、重试和 WKC 异常。
- [ ] 用示波器/逻辑分析仪核对至少一个 SPI 事务或输出时序。
- [ ] 保存配置、固件、抓包、照片、日志和失败复现脚本。

### 7.3 最终交付：从主站字节到物理动作

建议写一份 8-12 页的端到端报告，至少包含：

1. **版本矩阵**：主站、内核、网卡驱动、固件、板卡、ESI/SII。
2. **拓扑图**：接口、线缆、从站顺序、供电和测试负载。
3. **字段表**：应用中每个字段的类型、字节/位宽、PDO index/subindex。
4. **地址表**：iomap 偏移、逻辑地址、FMMU、SM、ESC 物理地址。
5. **帧证据**：一次输出和一次输入的完整抓包/十六进制。
6. **从站证据**：PDI 缓冲区、PDO 绑定对象、应用消费点。
7. **状态证据**：五个状态下的 AL Status/Status Code 和 SM 状态。
8. **时序证据**：p50/p99/max、回环延迟和一次超时故障。
9. **故障实验**：至少三个单变量故障及恢复过程。
10. **未验证项**：仿真与真实硬件之间仍未覆盖的边界。

如果报告能让他人只按文档复现实验并解释每个失败现象，才算真正完成。

## 9. 自检题与常见误区

### 9.1 系统与地址

1. 为什么 WKC 正常不能证明执行器已经动作？
2. 一个 `iomap` 偏移、一个 EtherCAT 逻辑地址和一个 ESC 物理地址分别属于谁？

4. 为什么“FMMU 配置正确”仍可能读错字段？
5. 一个帧经过 10 个从站，为什么不需要主站做 10 次请求/响应？
6. 如果最后一个从站掉线，哪些 WKC 检查会先暴露问题？

### 9.2 硬件与内存

7. `volatile` 能保证两个线程之间的原子性和顺序吗？
8. 什么情况下需要 `std::atomic`，什么情况下还需要 fence？
9. cache 与 DMA 的所有权问题如何产生“数据看似随机跳动”？

12. LAN9252 的 CSR 访问和 PRAM 访问分别可能有哪些等待/超时？
13. XMC4800 的内存映射 ESC 是否意味着访问没有硬件副作用？
14. SPI BYTE_TEST 失败时，应该先检查哪四类问题？

### 9.3 ESM、PDO 与邮箱

15. 主站写 `AL_CONTROL` 后，为什么要读 `AL_STATUS_CODE` 而不是只看目标状态？
16. 为什么错误上报要先写 code 再写 status？

18. 邮箱缓冲区与主机软件队列有什么区别？

24. 邮箱 debug 时，counter、toggle、can-read、can-write 各能说明什么？

### 9.4 实时、网络与看门狗

25. 平均周期 1 ms 是否代表最大周期 1 ms？
26. 为什么 `sleep(1ms)` 会累计漂移？绝对截止时间如何改善？
27. 中断合并为什么可能降低 CPU 占用却增加 EtherCAT 尾延迟？

29. 处理周期为什么应避免动态内存分配和不受控日志？

33. AF_XDP 能绕过什么，不能绕过什么？

### 9.5 工程实践

40. 升级 KickCAT 后，哪些源码假设和 `FEATURES.md` 结论需要重新核对？

### 9.6 十个危险误区

| 误区 | 正确认识 |
|---|---|
| WKC 对就说明 PDO 数据正确 | WKC 只证明预期访问发生，不证明字段语义或应用执行 |
| 达到 OP 就说明设备可以安全工作 | 还要验证输出值、看门狗、设备故障状态和硬件安全 |
| `volatile` 能解决多线程竞争 | 它主要表达 MMIO/可观察访问，不是原子同步 |
| 仿真通过就代表实时性通过 | 仿真不模拟真实 IRQ、PHY、cache、SPI 和调度抖动 |
| 平均延迟达标就满足实时要求 | 必须看 WCET、p99、max 和持续负载 |
| FMMU 映射就是把指针换一个地址 | 它是 ESC 网络侧的逻辑到物理地址机制 |
| SDO 成功就等于 ESI/SII/OD 一致 | 只证明本次对象访问成功，不代表 PDO/配置文件一致 |
| 看门狗越长越稳定 | 误触发减少，但故障反应变慢，必须平衡 |
| DC 打开就自动完成同步 | 还要验证参考时钟、传播延时、SYNC 和从站应用行为 |
| 关闭 WKC 检查能解决偶发错误 | 会把映射、掉线和干扰问题藏到业务层 |

## 10. 推荐阅读与源码顺序

### 10.1 源码阅读顺序

不要从最底层的 SPI 驱动一路读起，也不要只读 `main()`。推荐按“机制 → 状态 →
应用”的顺序：

| 顺序 | 文件/主题 | 回答的问题 |
|---:|---|---|
| 1 | `AbstractESC.h` | PDI/ESC 抽象统一了什么，没统一什么 |
| 2 | `ESC/Lan9252.*`、`ESC/XMC4800.*` | SPI 和内存映射两种物理路径如何工作 |
| 3 | `PDO.cc` | 映射、位宽、SM、缓冲区如何对应 |
| 4 | `ESM.cc`、`ESMStates.cc` | 状态、邮箱、PDO、看门狗如何互相约束 |
| 5 | `slave/Slave.cc` | 从站如何把邮箱、ESM、OD 和 PDO 组合起来 |
| 6 | `CoE/OD`、`Mailbox` | SDO 对象访问与邮箱语义 |
| 7 | `Bus.cc` 初始化/映射部分 | 主站如何配置 SM/FMMU/PDO |
| 8 | `Link.cc`、Socket 后端 | 帧如何发送、回调、超时和冗余 |
| 9 | `PERFORMANCE.md`、`Diagnostics` | 如何测量和诊断 |

### 10.2 规范与厂商资料

在本地 ETG 资料和主计划的基础上，优先补：

- ETG.1000.6：AL 状态机、SM、FMMU、PDO 的规范行为。
- ETG.2200：SubDevice 实现指南，帮助理解从站软件要做什么。
- `etg_doc/ESC_Overview.pdf`：ESC 模块和数据路径总览。
- LAN9252 数据手册：SPI、CSR、PRAM、busy、复位和 PDI 限制。
- XMC4800 Reference Manual：ESC 内存窗口、外设、中断和时钟。
- NuttX 官方文档：任务、信号量、时钟、SPI 驱动和交叉编译。
- Linux `AF_PACKET`、`AF_XDP`、RT scheduling 和网络 IRQ 文档。
- 所用从站/驱动器/IO 模块的 ESI 与设备手册，而不是只看通用规范。

规范描述“必须怎样”，厂商手册描述“这个芯片怎样实现”，源码描述“当前这个版本
实际怎样做”。三者不能互相替代。

### 10.3 文档—源码—实验的对应方式

每次学习一个概念，都填一行：

| 概念 | 规范定义 | KickCAT 位置 | 运行/实验证据 | 未验证边界 |
|---|---|---|---|---|
| 例：PDO 映射 | ETG.1000.6 mapping 规则 | `PDO::configureMapping` | bit 长度/缓冲区实验 | 真实设备多 SM |
| 例：过程数据看门狗 | ESC watchdog 规则 | `ESMStates.cc` OP 分支 | 仿真断流实验 | 实机时钟/恢复 |
| 例：SPI PDI | LAN9252 数据手册 | `Lan9252.cc` | 逻辑分析仪 | 信号完整性/极限负载 |

如果某一列写不出来，说明你目前得到的是“印象”，还不是可复用的工程知识。

## 11. 当前版本限制与结论边界

基于当前 KickCAT 快照，必须记住：

- 只按小端主机设计；跨大端平台时必须显式处理字节序。
- 每个从站当前支持一个输入 PDO SM 和一个输出 PDO SM；
  多 PDO SM 不能按已有实验外推。
- 真实从站侧 DC 尚未实现；主站 DC 仍为实验性功能。
- 仿真器不模拟中断，仿真正常不能覆盖 IRQ、逻辑分析仪和硬件实时行为。
- Windows 只适合工具和测试，不适合硬实时主站。
- LAN9252/XMC4800 的支持不代表任意 ESC、任意 MCU 或任意 PHY 自动可用。

本文的目标是建立主站工程师的系统判断力，不是替代以下专业工作：

- 硬件原理图/PCB/EMC 设计；
- 从站协议栈的完整产品化与认证；
- 功能安全评估；
- 电机和机械安全的系统设计。

与这些团队协作时，主站工程师至少要能提供：

- 准确的主站/固件/ESI 版本；
- 可复现的拓扑、帧、状态和时序证据；
- 明确区分协议、PDI、应用和物理层的假设；
- 单变量实验和失败恢复记录。

这比笼统地说“EtherCAT 不同步”或“从站有问题”有价值得多。
