邮箱三兄弟：EoE / FoE / SoE 逐字节拆开

CoE 之外，邮箱还承载三种协议：EoE 把以太网帧隧道进 EtherCAT，FoE 做文件读写（固件升级）， SoE 是老的伺服行规（SERCOS over EtherCAT）。它们共用同一个 6 字节邮箱头， 靠 Type 字段分流——但各自的协议头结构完全不同。

悬停字节看字段

EoE：把一整个以太网帧塞进邮箱

用途：给从站一个“以太网口”。典型场景是透过 EtherCAT 访问从站上的 HTTP 配置页、Modbus/TCP 网关、 或者用 TCP/IP 做参数服务器。EoE 不改变 EtherCAT 的实时通道，它只是复用邮箱。 ETG.1000.6 §5.7

EoE Header：4 字节

固定 4 字节，但字段的“切法”随服务类型变化：数据服务用 FragmentNumber + Offset + FrameNumber， 参数服务把同一位置解释成 Result。这是读 EoE 报文时最容易看错的地方。

一个完整 EoE 报文

6 B 邮箱头 + 4 B EoE 头 + 数据（可选 4 B 时间戳）。

邮箱头 EoE 头 以太网帧数据 时间戳

Length 字段 = 其后的邮箱服务数据长度（4 B EoE 头 + 数据 + 可选时间戳）。 数据部分的以太网帧不含前导码、SFD 和 FCS。

FrameType：先看第一个字节的低 4 位

分片机制：为什么要有 Fragment Number

邮箱大小通常只有 128–256 字节，一个 1500 字节的以太网帧必须切块。 EoE 按 32 字节为一个块（block），FragmentNumber 和 Offset 都以 block 为单位。 最后一个分片把 LastFragment 置 1，可选追加 4 字节时间戳。

CompleteSize = Trunc((以太网帧总字节数 + 31) / 32)，即总块数。 接收端按 FrameNumber + Offset 重组；同一个 FrameNumber 的分片必须按 offset 递增到达。

一次 EoE 会话的完整流程

FoE：文件读写，固件升级的底座

FoE 是一个极简的文件传输协议：Read / Write / Data / Ack / Error / Busy 六个操作码， 没有目录、没有权限模型（只有一个可选的 32 位密码）。固件升级就是 Write Request 打开文件，然后循环 Data / Ack。 ETG.1000.6 §5.8

FoE Header：2 字节

OpCode 1 字节 + Reserved 1 字节（必须为 0）。后面紧跟与 OpCode 对应的负载。 注意：2 字节头之后的所有多字节字段都是小端序。

Write Request 的真实字节

文件名 firmware.bin，密码 0x00000000（不用密码）。

邮箱头 FoE 头 负载

Data / Ack：一问一答的滑动窗口

Data Request

Packet Number 从 1 开始递增。数据区最大长度受邮箱大小限制， 通常一次 256–1000 字节。

Ack Request

从站回 Ack，Packet Number 回显。Packet Number = 0 表示“Ack 的是 Write Request”。 主站收到 Ack 才发下一个 Data。

完整固件下载时序

BOOT 状态：固件下载通常要求从站处于 BOOT（ESM 的 0x03），此时邮箱只允许 FoE。 有些从站允许在 INIT/PREOP 直接 FoE，但规范推荐走 BOOT，见 ESM 页。

SoE：SERCOS 伺服行规的邮箱通道

SoE 是早期伺服驱动沿用 SERCOS 参数模型（IDN）的邮箱协议。今天新设计大多直接用 CoE + CiA402， 但存量伺服、老设备、以及部分日系驱动仍然只支持 SoE。 ETG.1000.6 §5.6（邮箱 Type=0x05）· IEC 61800-7-204（SoE 本体）

先说明资料边界：本地的 ETG 文档只定义了 SoE 作为邮箱协议的存在 （Type = 0x05、AL Status Code 0x0045 MBX_SOE），没有给出 SoE 报文的逐字节结构。 下面关于报文字段的描述来自 IEC 61800-7-204 / SERCOS 行规，属于公开标准； 图中标 外部标准 的部分请以该标准原文为准，不要拿本站当规范。

SoE 报文的分层

SoE 复用邮箱的 6 字节头（Type=0x05），后面是 SoE 自己的头 + IDN + 数据。 IDN 是 16 位：高 4 位是元素/类型，低 12 位是参数号（S-0-xxxx / P-0-xxxx / C-0-xxxx 的 xxxx）。

邮箱头（Type=0x05） SoE 头 IDN / 数据

IDN 怎么读

S-0-0047位置指令值（Position command value）
S-0-0051位置反馈值 1
S-0-0036速度指令值
P-0-xxxx厂商/产品参数

S-0-0047 → IDN = 0x0047；元素 7（Data State）的 IDN = 0x7047。元素类型决定读回的是值、单位、最小/最大值还是名称。

SoE 的读写语义

读（Read）

主站→SoE Read Request（IDN, 元素）
从站→SoE Read Response（IDN, 值/状态）

SoE 是“按 IDN 寻址”的请求-响应，不像 CoE 的 SDO 有独立的索引/子索引和分段机制； 长数据靠 SoE 自己的多包机制（或直接受邮箱大小限制）。

写（Write）

主站→SoE Write Request（IDN, 数据）
从站→SoE Write Response（IDN, 结果码）

写参数时要带 Data State（元素 7）以确认“值已生效”；很多伺服要求先写参数、 再写 Data State = 1，否则重启后丢失。

怎么选

按用途

  • 参数/对象字典 → CoE（SDO）
  • 固件升级 → FoE
  • 从站上的 Web/Modbus/TCP → EoE
  • 存量伺服、SERCOS 参数 → SoE
  • 倍福体系 ADS → AoE

按“谁支持”

共同的三条铁律

①

邮箱只在 PREOP 及以上可用

INIT 只配 SM0/SM1；BOOT 只允许 FoE。想发邮箱，先把 ESM 推到 PREOP。

②

Length 不含邮箱头

Mailbox Header 的 Length 是“其后服务数据”的长度，不含这 6 字节本身。 这是算缓冲区时最常见的 off-by-6。

③

Cnt 与 Toggle 是两回事

邮箱头的 Cnt 是服务计数（1–7 循环），CoE SDO 的 Toggle 是分段序号； 两者独立，别混。

现场排查

EoE 能 ping 通但吞吐很低

EoE 走邮箱，每帧都要主站轮询 + 从站应答，本质是“停等”协议。吞吐受邮箱大小、主站轮询周期、 以及分片数限制。要高速率应该用过程数据或独立网口，而不是 EoE。

FoE 升到一半报 0x8005 Packet number wrong

主站重传了已确认的包，或从站丢了中间包。检查：① 主站是否等 Ack 再发下一包； ② 从站 Flash 擦除期间是否用 Busy 拖住；③ 邮箱缓冲区是否被其它协议（CoE/EoE）抢占。

SoE 写参数成功但重启丢失

只写了值，没写 Data State（元素 7）。SERCOS 模型要求写参数后写 Data State 确认生效并落盘。

邮箱报文长度对不上

先确认 Length 是“不含 6 字节头”的长度；再确认 EoE 的 CompleteSize 是 32 字节块数而不是字节数。
